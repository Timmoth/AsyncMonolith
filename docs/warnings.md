- **Single-instance or development with `AsyncMonolith.Ef`.** EF Core has no portable row locking, so with `AsyncMonolith.Ef` several app instances read the same candidate messages and compete for them. Claims are conditional, so a message is still only processed by one instance, but instances waste work. In production with several instances, use `AsyncMonolith.PostgreSql`, `AsyncMonolith.MsSql`, `AsyncMonolith.MySql` or `AsyncMonolith.MariaDb`, which lock rows and skip each other's batches.
- **Consumers run at least once.** A message can run again if the app stops mid-message, or if a consumer ignores its cancellation token and is abandoned. Make consumers idempotent: `ConsumeContext.MessageId` and `ConsumeContext.DeduplicationKey` help.
- **Honour the `CancellationToken`.** It is cancelled at the consumer's timeout and when the app stops.
- **Batches finish together.** A processor waits for every consumer in its batch before taking the next, so a slow consumer delays the others on its rail. Put slow consumers on their own rail with `[ConsumerRailId]`, or raise their `[ConsumerTimeout]`.
- **No ordering guarantee.** See [Ordering](guides/consuming-messages.md#ordering).
- **Test your expected throughput** against your database before relying on it.
